# 一時的な位置情報共有アプリ — Claude Code プロンプト

## 概要
待ち合わせ専用の一時的な位置情報共有アプリ。リンク発行→共有→完了で自動削除。

---

## Claude Code 実装プロンプト

```
以下の仕様で「一時的な位置情報共有アプリ」を実装してください。

## アプリ概要
- 待ち合わせ専用の一時的な位置情報共有アプリ
- ホストがリンクを発行 → ゲストがリンクを開く → 双方の位置をリアルタイム表示 → 完了ボタンで位置情報削除

## 技術スタック
- Frontend: React (Next.js) + TypeScript
- Backend: Node.js (Next.js API Routes or Express)
- リアルタイム通信: Socket.io
- DB: Redis（揮発性データ、TTL付き）
- 地図: Google Maps API または Mapbox GL JS
- デプロイ: Vercel or Railway

## 機能要件

### F-01 リンク発行
- ホームページに「待ち合わせを始める」ボタン
- ボタン押下でユニークなセッションID（UUID）を生成
- 共有URL例: https://example.com/meet/[sessionId]
- URLをコピー or LINEシェアボタン

### F-02 位置情報共有
- ホスト・ゲスト双方がブラウザのGeolocation APIで現在地を取得
- WebSocket（Socket.io）でリアルタイム送受信
- Google Maps or Mapbox上に2者のピンを表示
- 相手との距離をメートル表示

### F-03 完了操作
- 「完了」ボタン押下でセッション終了
- 位置情報の送信停止
- Redis上のセッションデータを即時削除
- 「待ち合わせ完了！位置情報を削除しました」画面に遷移

### F-04 自動失効
- セッション作成から6時間でRedisのTTL切れ → 自動無効化
- 期限切れURLアクセス時は「このリンクは有効期限切れです」と表示

### F-05 無登録利用
- アカウント登録不要
- セッションIDとトークン（JWT or HMAC）のみで認証

## 非機能要件
- HTTPS必須（Geolocation APIの要件）
- 完了後はサーバー上の位置データを即時削除（プライバシー優先）
- モバイルファーストのレスポンシブデザイン
- iOS Safariでのバックグラウンド位置情報制限に対応（フォアグラウンド前提で設計）

## 画面構成
1. /        → ホーム（リンク生成ボタン）
2. /meet/[id] → マップ画面（双方の現在地 + 完了ボタン）
3. /done    → 終了画面（削除完了メッセージ）
4. /expired → 期限切れ画面

## セキュリティ
- セッションIDはUUID v4
- アクセストークンをURLクエリパラメータに付与してなりすまし防止
- Redis保存データは位置情報のみ（個人情報は保存しない）

## 実装手順
1. Next.jsプロジェクト作成 (TypeScript)
2. Redis接続設定（ioredis）
3. Socket.ioサーバー設定
4. セッション生成APIの実装
5. Geolocation + Socket.io クライアント実装
6. Google Maps / Mapbox 地図表示実装
7. 完了ボタン → データ削除フロー実装
8. UI/UXの仕上げ（モバイル対応）
9. Vercelデプロイ設定
```

## 複数ルーム対応設計（ハイター × フランメ 検討）

### 企画観点（ハイター）

複数の待ち合わせを同時管理できると、グループ行動・イベント幹事・チーム分散移動などで価値が上がる。
ユースケース：
- 合コン幹事が男女2班を同時管理
- フェス・旅行で複数チームを一元把握
- 迷子のときに親と子で別ルームを立てる

### UX設計案

| 画面 | 内容 |
|------|------|
| / ホーム | 「新しい待ち合わせ」ボタン ＋ 既存ルーム一覧 |
| /dashboard | 自分が作ったルームのカード一覧（ルーム名・参加者数・状態） |
| /meet/[id] | 従来通りのマップ画面（変更なし） |

- ルームに**名前をつけられる**（例：「新宿改札口」「渋谷スタバ」）
- ルームカードに**残り時間**と**参加人数**を表示
- 一括「全て完了」ボタンでまとめて解散

### 技術設計案

```
## 追加機能要件（複数ルーム対応）

### F-06 ルーム管理
- ホストはセッション作成時にルーム名（任意）を設定可能
- ホストのブラウザローカルストレージに作成済みルームID一覧を保存
- /dashboard で自分のルーム一覧を表示（リロードしても復元）

### F-07 複数ルーム同時起動
- 各ルームは独立したSocket.io roomとして管理
- Redisキー設計: `room:{sessionId}:meta`（ルーム名・作成時刻）
                  `room:{sessionId}:users:{userId}`（位置情報）
- ルーム数上限: ホスト1人あたり最大5ルームまで（Redis負荷対策）

### F-08 ダッシュボード
- GET /api/rooms?ids=[id1,id2,...] で複数ルームのメタ情報を一括取得
- 参加者数はSocket.io room.size で取得
- 状態: active / completed / expired の3種

### データモデル追加
Redis:
- room:{id}:meta → { name, createdAt, status, hostToken }
- room:{id}:members → Set of userIds

localStorage（クライアント）:
- myRooms → [ { id, name, createdAt } ]
```

### 実装追加手順
1. ルーム名入力UI（ホーム画面に追加）
2. `/api/rooms/create` APIにname フィールド追加
3. localStorageへのルームID保存ロジック
4. `/dashboard` ページ新規作成
5. ルーム一覧取得API `/api/rooms?ids=...` 実装
6. 「全て完了」一括終了API

## フランメ追記：マーケティング・UX戦略観点

### ターゲット別ユースケース優先度

| ターゲット | ユースケース | 訴求ポイント |
|-----------|------------|------------|
| イベント幹事 | 複数班の同時管理 | 「一画面で全員を把握」 |
| 旅行グループ | A班・B班の分散移動 | 「バラバラでも安心」 |
| 合コン幹事 | 男女2グループを誘導 | 「気まずくならない導線」 |
| 親子 | 迷子対策ルーム | 「すぐ共有、すぐ消える安心感」 |

### UXコピー案（ルーム名のプレースホルダー）
- 「どこで待ち合わせ？（例：北口の改札）」
- 名前がつくとルームが"場所"として認識される → 完了率UP

### SNS拡散設計
- 完了画面に「このアプリをシェア」ボタン追加
- 「位置情報は消えた🗑️ #安心待ち合わせ」のテンプレツイート
- ルームURL自体がSNSシェアの入口になる設計を意識

### 差別化ポイント（競合対策）
1. **登録ゼロ**：LINEに頼らない位置共有
2. **完全揮発**：プライバシーに敏感なユーザーへの訴求
3. **複数ルーム**：幹事ユースケースでの独自価値
