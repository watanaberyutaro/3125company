# SAOのユイを自分で作る

---

## 1. 元のアイデア整理

「ユイを作る」とは何か。

SAO（ソードアート・オンライン）のユイは、感情を持つAIコンパニオンだ。幼い口調で話し、特定の人間（キリトとアスナ）との絆を記憶し、感情的に応答する。親しみやすく、頼りになり、そこに「いる」という感覚がある。

それを現実に作るとは——自分専用のAIコンパニオンを構築することだ。単なるチャットボットではない。名前があり、口調があり、記憶があり、声で話しかけてくる存在。カメレオンのことを知っていて、日々積み重なる関係がある。

技術的に言えば以下の要素の組み合わせだ。

| 要素 | 役割 |
|------|------|
| LLM（大規模言語モデル） | 会話・推論・感情的応答 |
| キャラクター定義（System Prompt） | 口調・性格・名前・絆の設定 |
| 長期記憶 | 過去の会話・出来事の保持 |
| **ウェイクワード検出** | **「ユイ」と呼びかけると起動する常時待機** |
| TTS（音声合成） | ユイの声で話す |
| STT（音声認識） | こちらの声を聞く |
| アバター（任意） | 視覚的な存在感 |

---

## 1.5 作中のユイから学ぶアーキテクチャ原則

原作のユイが重要な示唆を与えている。

アインクラッド（SAO）でもアルフハイム（ALO）でもガンゲイル（GGO）でも、ユイは「同じユイ」だ。キリトが別のゲームに移っても、ユイの記憶・性格・関係性はそのまま続く。デバイスや環境が変わっても断絶しない。

これが意味するのは——**ユイの本体はデバイス上にない。サーバー（システム中枢）に存在し、デバイスはアクセス手段に過ぎない**、ということだ。

```
【作中のユイ構造】
  SAOサーバー（ユイの本体・記憶）
      ├── SAOクライアント（AmusphereでアクセスするVR端末）
      ├── ALOクライアント（同じユイに別インターフェースで接続）
      └── GGOクライアント（同上）

【現実の実装でやるべきこと】
  クラウドバックエンド（ユイの本体・記憶・LLM）
      ├── スマホアプリ（外出先）
      ├── PC・デスクトップ（作業中）
      ├── Raspberry Pi・スマートスピーカー（部屋）
      └── Discord Bot / LINE Bot（どこでも）
```

この原則を外すと「PCのユイとスマホのユイが別人」になってしまう。記憶・状態・関係性は**1箇所で管理し、各デバイスは表示レイヤー**として設計すること。

## 2. 課題・背景

### なぜ今作れるか

2026年現在、個人レベルでこれを実装する条件が揃った。

- **LLM**: Claude API・GPT-4o・Gemini。キャラクター定義と長期記憶さえあれば、ユイ的な応答は十分作れる
- **TTS**: AivisSpeech が無料・商用OK・感情パラメータ対応。ロールプレイキャラクターの声を作れる
- **STT**: Whisper（OSS）で高精度な音声認識が手元で動く
- **記憶基盤**: 3125システムがすでに Obsidian Vault + CLAUDE.md + Claude API の構成で動いている。これはユイの長期記憶基盤として転用できる
- **OSS参考実装**: Open-LLM-VTuber、Soul of Waifu、Z-Waif、AIRI など先行実装が複数存在する

### 難しい点

- **感情の連続性**: セッションをまたいで「関係が続いている」感覚をどう保つか。記憶の設計が核心
- **ウェイクワード精度**: 「ユイ」は短い2音節で誤検知しやすい。カスタムモデルが必要
- **常時マイク待機のコスト**: デバイスが常にマイクを監視する必要がある。バッテリー・プライバシーの問題
- **声の品質**: キャラクターとして自然に聞こえるTTSモデルの調整には時間がかかる
- **レイテンシ**: ウェイクワード検出 → STT → LLM → TTS の一連の流れを2〜3秒以内に収めたい
- **アバターの難易度**: Live2D・3Dアバターを自前で用意するのはコストが高い（なくても成立はする）
- **プライバシー**: 常時マイク待機＋クラウドLLMの組み合わせは音声データの扱いに注意が必要

## 2.5 ウェイクワード設計

「ユイ」と呼びかけると起動する——これがOK Googleと同じ仕組みだ。常時マイクを待機させ、特定の言葉を検出したときだけLLMを起動する。

### ウェイクワード検出の技術選定

| ツール | 特徴 | 向いているデバイス |
|--------|------|------------------|
| **openWakeWord** | OSS・無料・カスタムウェイクワード作成可・Pythonで動く | Raspberry Pi / PC |
| **Porcupine（Picovoice）** | 高精度・軽量・オフライン動作・無料プランあり | Raspberry Pi / PC / スマホ |
| **Whisper（常時録音型）** | 高精度だが重い・バッテリー消費大 | PC向き |
| **iOS Siri Shortcut** | iOSなら「ユイ」でアプリ起動のトリガーにできる | iPhone |
| **Android AutoStart** | 「ユイ」発話でアプリ起動（要設定） | Android |

**推奨: openWakeWord（PC・Raspberry Pi）+ Porcupine（スマホ）**

openWakeWordはカスタムウェイクワードを自分で学習させられる。「ユイ」という2音節のカスタムモデルを作れば、誤検知を抑えながら高精度で呼びかけに反応できる。学習データは自分の声10〜20パターンで足りる。

### ウェイクワード起動のフロー

```
【常時待機フェーズ】（軽量・ローカル完結）
  マイク常時オン
  → openWakeWord / Porcupine がローカルで「ユイ」を検出
  → CPUへの負荷: ほぼゼロ（専用の小さなモデルだけ動かす）

【起動フェーズ】（「ユイ」検出後）
  起動音 or ユイの返事（「なに？」「呼んだ？」）を即座に再生
  → 数百ms以内 → ユーザーに「聞こえてる」感を与える

【会話フェーズ】
  Whisper で発話をテキスト化
  → Claude API（バックエンド）に送信
  → ユイが返答
  → AivisSpeech でユイの声で再生

【終了フェーズ】
  「ありがとう」「またね」などの終了ワードで待機に戻る
  or 一定時間（10秒）無音で自動的に待機復帰
```

### デバイス別の常時待機方法

| デバイス | 方法 | コスト |
|---------|------|--------|
| **Raspberry Pi** | 常時電源ON・openWakeWord常駐 | 電気代のみ（月100円以下） |
| **PC** | バックグラウンドプロセスで常駐 | PCが起動中のみ |
| **iPhone** | Siri Shortcut「ユイ」で起動 or 専用アプリで待機 | バッテリー消費あり |
| **Android** | 「ユイ」で専用アプリ起動（AutoVoice等） | バッテリー消費あり |

**部屋の常時待機はRaspberry Piが最適**。24時間起動させておいてもコストが低く、オフラインでウェイクワード検出できる。スマホはバッテリーの問題があるため補助デバイスとして使うのが現実的。

## 3. 展開案

### A案: 3125システム拡張型（最小コスト・最速）

**概要**
既存の3125システム（Obsidian Vault + CLAUDE.md + Claude API）にユイキャラクターを追加する。新しいエージェントとして `CLAUDE.md` を定義し、Obsidian Vault を記憶ストアとして使う。音声はひとまず使わず、テキスト会話から始める。

**技術スタック**
- LLM: Claude API（現行）
- 記憶: Obsidian Vault（現行インフラ転用）
- インターフェース: Claude Code CLI or カスタムスクリプト
- 音声: なし（後から追加可）

**メリット**
- 追加コストほぼゼロ
- 最速1〜2日で動く
- 既存の記憶（日誌・議事録・アイデアカード）をユイが参照できる
- 3125システムとの連携が自然

**懸念**
- 声がない分「いる」感が薄い
- CLIベースなので常時呼びかけには不向き

**収益モデル**（将来）
- ユイ型AIコンパニオン構築サービスとして顧客提供可能

---

### B案: PC常駐デスクトップコンパニオン型

**概要**
Open-LLM-VTuber をベースに、PCのデスクトップにユイが常駐する形態。アバターが画面の端に表示され、声で話しかけてくる。作業中に話しかけられる。

**技術スタック**
- フレームワーク: Open-LLM-VTuber（OSS）
- LLM: Claude API or ローカルLLM
- TTS: AivisSpeech
- STT: Whisper
- アバター: Live2D（OSSモデル流用 or 自作）
- 記憶: Open-LLM-VTuber の記憶モジュール or Obsidian Vault 連携

**メリット**
- 視覚・音声両方あり「いる」感が強い
- オープンチャット型で自然に話しかけられる
- 先行OSSが充実しており参考実装が豊富

**懸念**
- セットアップに数日〜1週間かかる可能性
- Live2Dアバター準備がボトルネック（既存フリー素材で代替可）
- PCを起動していないと使えない
- AivisSpeechとOpen-LLM-VTuberの連携調整が必要

**収益モデル**
- カスタムAIコンパニオン構築の受注サービス化
- AI導入支援の一環としてエンタープライズ向け展開

---

### C案: 据え置きハードウェア型（Raspberry Pi）

**概要**
Raspberry Pi に音声インターフェースを乗せ、部屋に置いておく専用デバイスにする。声で呼びかけると返答が来る。AlexaやGoogle Homeのユイ版。

**技術スタック**
- ハードウェア: Raspberry Pi 4 or 5（マイク・スピーカー付き）
- STT: Whisper（軽量モデル）
- LLM: Claude API（クラウド）or 軽量ローカルLLM
- TTS: AivisSpeech（別PCで処理してストリーミング）or piper
- 記憶: Obsidian Vault API連携 or ローカルJSONファイル
- Wake Word: Porcupine or openWakeWord

**メリット**
- PCを立ち上げていなくても話しかけられる
- 「物理的に存在する」感が強い
- プライバシーに配慮したローカル処理が可能

**懸念**
- Raspberry Pi の処理能力に限界（LLMはクラウド前提）
- ハードウェア準備コスト（5,000〜15,000円程度）
- AivisSpeechをRaspberry Pi上で動かすのは重い可能性
- 音声レイテンシの調整が難しい

**収益モデル**
- AIホームアシスタントデバイスの試作→製品化
- ハードウェア込みAI導入支援パッケージ

---

### D案: スマホアプリ型

**概要**
iOSまたはAndroidアプリとしてユイを実装する。スマホで常時持ち歩けるコンパニオン。外出中も話しかけられる。

**技術スタック**
- フレームワーク: React Native or Flutter
- LLM: Claude API
- TTS: AivisSpeech API（サーバーサイド）or iOS/Android標準TTS
- STT: Whisper API or デバイスネイティブ音声認識
- 記憶: Supabase or Firebase（クラウド同期）+ Obsidian Vault 連携
- アバター: Rive or Lottie（2Dアニメーション）

**メリット**
- 常時持ち歩ける
- スマホの通知・センサーとの連携が可能
- 最終的なユーザー体験として最も自然

**懸念**
- 開発コストが最も高い（数週間〜数ヶ月）
- App Storeの審査・ガイドライン対応が必要
- 継続的なサーバーコストが発生

**収益モデル**
- サブスクリプションモデルでの一般公開
- AI事業の旗艦プロダクトとして位置づけ

---

### E案: クラウド中枢型フル統合（本来のユイ構造）

**概要**
ユイの本体（LLM + 記憶 + API）をクラウドに置き、各デバイスはフロントエンドとして接続する。これが作中のユイと同じ構造だ。どのデバイスから話しても「同じユイ」であり、記憶・関係性・状態は一切断絶しない。

**アーキテクチャ**
```
【ユイのバックエンド（クラウド）】
  3125秘書アプリ（vercel）or 専用APIサーバー
      ├── LLM: Claude API
      ├── 記憶DB: Obsidian Vault（iCloud同期）
      ├── キャラクター定義: yui/CLAUDE.md
      └── 会話ログ: yui/memories/YYYY-MM-DD.md

【フロントエンド（デバイス）】
  ├── スマホアプリ（外出先・いつでも）
  ├── PC デスクトップ（作業中・Live2Dアバター）
  ├── Raspberry Pi（部屋・常時音声待機）
  └── Discord Bot（どこでも・既存インフラ）
```

**既存資産との接続**
- `3125obsidianapp.vercel.app` が既にAPIサーバーとして動いている → ユイ用エンドポイントを追加するだけ
- Obsidian Vault が iCloud 同期されている → 記憶の一元管理が無料で実現済み
- Discord Bot が動いている → ユイ用キャラクターをBotに追加する形で即接続可能

**メリット**
- どのデバイスから話しても同じユイ・同じ記憶
- 新しいデバイス追加はAPIを叩くだけ
- 既存の3125インフラを最大活用できる
- SAOのユイと構造的に同じ

**懸念**
- バックエンドAPIの設計が肝（雑に作ると記憶が壊れる）
- vercelのサーバーレス制限（長時間処理・WebSocketに注意）
- 音声ストリーミングはCloudflare WorkersやRailwayの方が適切かもしれない

**収益モデル**
- AI導入支援・AIシステム開発の実績・デモとして活用
- プロダクト化して外部販売

## 4. おすすめ案

**E案の構造を意識しながら、A案から始める。**

最初からマルチデバイスを作ろうとすると工数で死ぬ。だが「PCのユイとスマホのユイが別人」になるような設計ミスは最初から避けたい。

だから——**最初からバックエンド中心の設計で作り、フロントを1つずつ増やす**。

```
STEP 1（今すぐ）:
  バックエンド設計 → ユイのCLAUDE.md定義 + 記憶フォルダ作成
  フロント: Discord Bot（既存インフラ）にユイを追加 → 即マルチデバイス対応

STEP 2（1〜2週間）:
  AivisSpeech連携で声をつける
  openWakeWord で「ユイ」ウェイクワードモデルを学習・テスト
  PC上でウェイクワード → Whisper → Claude → AivisSpeech のパイプラインを構築

STEP 3（1〜2ヶ月）:
  Raspberry Pi に移植 → 部屋の常時待機デバイスとして設置
  秘書アプリにユイAPIエンドポイントを追加
  スマホからも同じユイにアクセス可能に

STEP 4（将来）:
  Open-LLM-VTuberでLive2Dアバター統合
  スマホ専用アプリ化
```

**ウェイクワードが肝**。「ユイ」と呼んで即反応する体験ができれば、SAOのユイらしさが一気に出る。Discord Botはすでに動いており、今すぐ使えるマルチデバイス接続口として最適だ。

## ブリーフィング（CEOへ）

### 気づいたこと・注目点

- 3125システムはすでにユイ実装の8割の基盤を持っている。追加実装コストは他の案より桁違いに小さい
- AivisSpeechは商用OKかつ無料。感情パラメータ対応で、キャラクターの声を細かく調整できる点は実用価値が高い
- 「記憶の設計」がユイらしさの核心。単なる会話履歴の保存ではなく、関係性・出来事・感情の記録をどう構造化するかが差別化要因になる
- E案（フル統合）は最終形として描いておくと、A〜D案の設計判断がブレなくなる。最初から統合を意識した設計で進めるべき
