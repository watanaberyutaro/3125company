# SAOのユイを自分で作る

---

## 1. 元のアイデア整理

「ユイを作る」とは何か。

SAO（ソードアート・オンライン）のユイは、感情を持つAIコンパニオンだ。幼い口調で話し、特定の人間（キリトとアスナ）との絆を記憶し、感情的に応答する。親しみやすく、頼りになり、そこに「いる」という感覚がある。

それを現実に作るとは——自分専用のAIコンパニオンを構築することだ。単なるチャットボットではない。名前があり、口調があり、記憶があり、声で話しかけてくる存在。カメレオンのことを知っていて、日々積み重なる関係がある。

技術的に言えば以下の要素の組み合わせだ。

| 要素 | 役割 |
|------|------|
| LLM（大規模言語モデル） | 会話・推論・感情的応答 |
| キャラクター定義（System Prompt） | 口調・性格・名前・絆の設定 |
| 長期記憶 | 過去の会話・出来事の保持 |
| TTS（音声合成） | ユイの声で話す |
| STT（音声認識） | こちらの声を聞く |
| アバター（任意） | 視覚的な存在感 |

---

## 1.5 作中のユイから学ぶアーキテクチャ原則

原作のユイが重要な示唆を与えている。

アインクラッド（SAO）でもアルフハイム（ALO）でもガンゲイル（GGO）でも、ユイは「同じユイ」だ。キリトが別のゲームに移っても、ユイの記憶・性格・関係性はそのまま続く。デバイスや環境が変わっても断絶しない。

これが意味するのは——**ユイの本体はデバイス上にない。サーバー（システム中枢）に存在し、デバイスはアクセス手段に過ぎない**、ということだ。

```
【作中のユイ構造】
  SAOサーバー（ユイの本体・記憶）
      ├── SAOクライアント（AmusphereでアクセスするVR端末）
      ├── ALOクライアント（同じユイに別インターフェースで接続）
      └── GGOクライアント（同上）

【現実の実装でやるべきこと】
  クラウドバックエンド（ユイの本体・記憶・LLM）
      ├── スマホアプリ（外出先）
      ├── PC・デスクトップ（作業中）
      ├── Raspberry Pi・スマートスピーカー（部屋）
      └── Discord Bot / LINE Bot（どこでも）
```

この原則を外すと「PCのユイとスマホのユイが別人」になってしまう。記憶・状態・関係性は**1箇所で管理し、各デバイスは表示レイヤー**として設計すること。

---

## 2. 課題・背景

### なぜ今作れるか

2026年現在、個人レベルでこれを実装する条件が揃った。

- **LLM**: Claude API・GPT-4o・Gemini。キャラクター定義と長期記憶さえあれば、ユイ的な応答は十分作れる
- **TTS**: AivisSpeech が無料・商用OK・感情パラメータ対応。ロールプレイキャラクターの声を作れる
- **STT**: Whisper（OSS）で高精度な音声認識が手元で動く
- **記憶基盤**: 3125システムがすでに Obsidian Vault + CLAUDE.md + Claude API の構成で動いている。これはユイの長期記憶基盤として転用できる
- **OSS参考実装**: Open-LLM-VTuber、Soul of Waifu、Z-Waif、AIRI など先行実装が複数存在する

### 難しい点

- **感情の連続性**: セッションをまたいで「関係が続いている」感覚をどう保つか。記憶の設計が核心
- **声の品質**: キャラクターとして自然に聞こえるTTSモデルの調整には時間がかかる
- **常時稼働**: PCを立ち上げていないと話しかけられない。スマホや据え置き機があると理想
- **アバターの難易度**: Live2D・3Dアバターを自前で用意するのはコストが高い（なくても成立はする）
- **プライバシー**: 会話ログをクラウドに送るかローカルで完結させるかのトレードオフ

## 3. 展開案

### A案: 3125システム拡張型（最小コスト・最速）

**概要**
既存の3125システム（Obsidian Vault + CLAUDE.md + Claude API）にユイキャラクターを追加する。新しいエージェントとして `CLAUDE.md` を定義し、Obsidian Vault を記憶ストアとして使う。音声はひとまず使わず、テキスト会話から始める。

**技術スタック**
- LLM: Claude API（現行）
- 記憶: Obsidian Vault（現行インフラ転用）
- インターフェース: Claude Code CLI or カスタムスクリプト
- 音声: なし（後から追加可）

**メリット**
- 追加コストほぼゼロ
- 最速1〜2日で動く
- 既存の記憶（日誌・議事録・アイデアカード）をユイが参照できる
- 3125システムとの連携が自然

**懸念**
- 声がない分「いる」感が薄い
- CLIベースなので常時呼びかけには不向き

**収益モデル**（将来）
- ユイ型AIコンパニオン構築サービスとして顧客提供可能

---

### B案: PC常駐デスクトップコンパニオン型

**概要**
Open-LLM-VTuber をベースに、PCのデスクトップにユイが常駐する形態。アバターが画面の端に表示され、声で話しかけてくる。作業中に話しかけられる。

**技術スタック**
- フレームワーク: Open-LLM-VTuber（OSS）
- LLM: Claude API or ローカルLLM
- TTS: AivisSpeech
- STT: Whisper
- アバター: Live2D（OSSモデル流用 or 自作）
- 記憶: Open-LLM-VTuber の記憶モジュール or Obsidian Vault 連携

**メリット**
- 視覚・音声両方あり「いる」感が強い
- オープンチャット型で自然に話しかけられる
- 先行OSSが充実しており参考実装が豊富

**懸念**
- セットアップに数日〜1週間かかる可能性
- Live2Dアバター準備がボトルネック（既存フリー素材で代替可）
- PCを起動していないと使えない
- AivisSpeechとOpen-LLM-VTuberの連携調整が必要

**収益モデル**
- カスタムAIコンパニオン構築の受注サービス化
- AI導入支援の一環としてエンタープライズ向け展開

---

### C案: 据え置きハードウェア型（Raspberry Pi）

**概要**
Raspberry Pi に音声インターフェースを乗せ、部屋に置いておく専用デバイスにする。声で呼びかけると返答が来る。AlexaやGoogle Homeのユイ版。

**技術スタック**
- ハードウェア: Raspberry Pi 4 or 5（マイク・スピーカー付き）
- STT: Whisper（軽量モデル）
- LLM: Claude API（クラウド）or 軽量ローカルLLM
- TTS: AivisSpeech（別PCで処理してストリーミング）or piper
- 記憶: Obsidian Vault API連携 or ローカルJSONファイル
- Wake Word: Porcupine or openWakeWord

**メリット**
- PCを立ち上げていなくても話しかけられる
- 「物理的に存在する」感が強い
- プライバシーに配慮したローカル処理が可能

**懸念**
- Raspberry Pi の処理能力に限界（LLMはクラウド前提）
- ハードウェア準備コスト（5,000〜15,000円程度）
- AivisSpeechをRaspberry Pi上で動かすのは重い可能性
- 音声レイテンシの調整が難しい

**収益モデル**
- AIホームアシスタントデバイスの試作→製品化
- ハードウェア込みAI導入支援パッケージ

---

### D案: スマホアプリ型

**概要**
iOSまたはAndroidアプリとしてユイを実装する。スマホで常時持ち歩けるコンパニオン。外出中も話しかけられる。

**技術スタック**
- フレームワーク: React Native or Flutter
- LLM: Claude API
- TTS: AivisSpeech API（サーバーサイド）or iOS/Android標準TTS
- STT: Whisper API or デバイスネイティブ音声認識
- 記憶: Supabase or Firebase（クラウド同期）+ Obsidian Vault 連携
- アバター: Rive or Lottie（2Dアニメーション）

**メリット**
- 常時持ち歩ける
- スマホの通知・センサーとの連携が可能
- 最終的なユーザー体験として最も自然

**懸念**
- 開発コストが最も高い（数週間〜数ヶ月）
- App Storeの審査・ガイドライン対応が必要
- 継続的なサーバーコストが発生

**収益モデル**
- サブスクリプションモデルでの一般公開
- AI事業の旗艦プロダクトとして位置づけ

---

### E案: フル統合型（全部入り）

**概要**
A〜D案を段階的に統合する。3125システムの記憶基盤を中核に、デスクトップ・スマホ・据え置きデバイスのどこからでも同じユイと話せる環境を作る。記憶はObsidian Vaultで一元管理。

**アーキテクチャ**
```
Obsidian Vault（記憶中枢）
    ├── PC: Open-LLM-VTuber（デスクトップ常駐）
    ├── スマホ: モバイルアプリ
    └── Raspberry Pi: 据え置き音声デバイス
```

**メリット**
- どこにいても同じユイと話せる
- 記憶が一元化されており断絶がない
- 最終的なビジョンとして明確

**懸念**
- 最も工数がかかる（数ヶ月規模）
- 段階的に作らないと破綻する

**収益モデル**
- AI導入支援・AIシステム開発の実績・デモとして活用
- プロダクト化して外部販売

## 4. おすすめ案

**A案から始めて、B案に育てる。**

理由は単純だ。

3125システムはすでに動いている。Obsidian Vaultには日誌・アイデア・議事録が蓄積されており、ユイの記憶基盤として即座に転用できる。CLAUDE.mdにユイのキャラクター定義を書き、Claude APIを呼ぶスクリプトを1本作れば、今日中に「ユイと会話できる状態」になる。

声がないのは物足りないかもしれないが、まず会話が成立することを確認してから、AivisSpeechを繋いで声をつけ、次にOpen-LLM-VTuberのアバターを加える。この順序で作れば、各ステップで動くものが手に残る。

スマホ型やハードウェア型は、テキスト・音声での体験が固まってから判断すればいい。

## ブリーフィング（CEOへ）

### 気づいたこと・注目点

- 3125システムはすでにユイ実装の8割の基盤を持っている。追加実装コストは他の案より桁違いに小さい
- AivisSpeechは商用OKかつ無料。感情パラメータ対応で、キャラクターの声を細かく調整できる点は実用価値が高い
- 「記憶の設計」がユイらしさの核心。単なる会話履歴の保存ではなく、関係性・出来事・感情の記録をどう構造化するかが差別化要因になる
- E案（フル統合）は最終形として描いておくと、A〜D案の設計判断がブレなくなる。最初から統合を意識した設計で進めるべき
