# Webセキュリティ学習ロードマップ（Vercel・Supabase・Git スタック向け）

## 調査背景

AI導入支援・受託開発・Web制作を手がける個人開発者として、Vercel（Next.js）・Supabase・Gitを日常的に使う立場から、「致命的なミスをしない」「スケール時に困らない」レベルのWebセキュリティ知識を体系的に習得するためのロードマップ。専門家になることが目的ではなく、**実害につながる穴を塞ぐ**ことに特化して整理した。

---

## 1. Webセキュリティの基礎知識

### 1-1. OWASP Top 10（2021版）概要と優先度

OWASP Top 10はWebアプリケーションに対する最も重大なセキュリティリスクを示した業界標準ドキュメント。2021年版では2017年版から大きく構成が変化した。

| 順位 | カテゴリ | 概要 | 個人開発者の優先度 |
|------|---------|------|------------------|
| A01 | アクセス制御の不備 | 認証なしに他ユーザーのデータへアクセスできる。2017年版5位から1位に急浮上 | ★★★ 最重要 |
| A02 | 暗号化の失敗 | 平文での通信・保存、古い暗号アルゴリズムの使用 | ★★★ |
| A03 | インジェクション | SQLインジェクション・コマンドインジェクション等。XSSもここに含まれる | ★★★ |
| A04 | 安全が確認されない不安な設計 | セキュリティを後付けではなく設計段階で組み込む考え方 | ★★ |
| A05 | セキュリティの設定ミス | デフォルト設定のまま運用、不要な機能の有効化 | ★★★ |
| A06 | 脆弱で古くなったコンポーネントの使用 | 既知脆弱性のあるnpmパッケージ等 | ★★ |
| A07 | 識別と認証の失敗 | パスワード管理の不備、セッション固定攻撃 | ★★★ |
| A08 | ソフトウェアとデータの整合性の不具合 | CI/CDパイプラインへの不正な介入、安全でないデシリアライズ | ★★ |
| A09 | セキュリティログとモニタリングの不備 | 攻撃を検知・記録できない状態 | ★ |
| A10 | サーバーサイドリクエストフォージェリ（SSRF） | サーバーを踏み台にした内部リソースへのアクセス | ★ |

**出典**: [OWASP Top 10:2021](https://owasp.org/Top10/2021/) / [yamory: 2021年版 OWASP Top 10 概要](https://yamory.io/blog/2021-owasp-top-10)

### 1-2. 開発者として最低限知るべき攻撃手法

#### XSS（クロスサイトスクリプティング）

- **仕組み**: ユーザーの入力値をそのままHTMLに埋め込むことで、悪意のあるスクリプトを実行させる
- **被害**: セッションの盗用、フィッシング、マルウェア配布
- **Next.jsでの対策**:
  - Reactはデフォルトでエスケープ処理するが、`dangerouslySetInnerHTML` を使う場合は `DOMPurify` でサニタイズ必須
  - `next.config.js` または Middleware でCSP（Content Security Policy）ヘッダーを設定する
  - セキュリティヘッダー例: `X-XSS-Protection`, `X-Content-Type-Options`, `Content-Security-Policy`

```js
// next.config.js でのセキュリティヘッダー設定例
const securityHeaders = [
  { key: 'X-Content-Type-Options', value: 'nosniff' },
  { key: 'X-Frame-Options', value: 'DENY' },
  { key: 'X-XSS-Protection', value: '1; mode=block' },
  {
    key: 'Content-Security-Policy',
    value: "default-src 'self'; script-src 'self' 'nonce-{NONCE}' 'strict-dynamic';"
  }
]
```

#### SQLインジェクション

- **仕組み**: 入力値にSQL文を混入させ、データベースを不正操作する
- **被害**: 全データの窃取・改ざん・削除
- **Supabaseでの対策**: Supabaseは内部的にPostgRESTを使用しており、パラメータ化クエリがデフォルト。ただし `rpc()` でRaw SQLを書く場合は自前でサニタイズが必要

#### CSRF（クロスサイトリクエストフォージェリ）

- **仕組み**: ユーザーが意図しないリクエストを別サイトから送信させる
- **被害**: パスワード変更、送金、データ削除
- **Next.jsでの対策**:
  - `SameSite=Strict` または `SameSite=Lax` のCookie属性を設定
  - CSRFトークンを使用（Server ActionsはNext.js 14以降でデフォルト保護あり）
  - `Origin` ヘッダーを検証

#### 認証・認可の不備（最多発生リスク）

- **仕組み**: APIエンドポイントの認可チェック漏れ、他ユーザーのリソースへのアクセス
- **Next.jsでの対策**: Server Actionsは誰でも直接POSTできる。UI側の制御だけでなく、**アクション内で必ず認証・認可チェックを実施**すること

**出典**: [Zenn: 実践で学ぶWebセキュリティ Next.js + FastAPI](https://zenn.dev/fumi_mizu/articles/9d959aa2d6ebe3) / [GMO Flatt Security Blog: インジェクション脆弱性](https://blog.flatt.tech/entry/how_to_deal_with_injection_vulnerabilities)

## 2. スタック別セキュリティ実践

### 2-1. Supabase セキュリティ

#### RLS（Row Level Security）設計

RLSはSupabaseのセキュリティの根幹。これを正しく設計できるかどうかで、致命的なデータ漏洩を防げるかが決まる。

**絶対に守るべきルール:**

1. **publicスキーマの全テーブルでRLSを有効にする**。デフォルトはOFFなので、テーブル作成時に必ず有効化
2. **`user_metadata` をRLSポリシーで使わない**。ユーザー自身が書き換えられるため、セキュリティホールになる
3. **ロールを明示的に指定する**。`auth.uid()` だけでなく、`TO authenticated` を必ず追加する
4. **インデックスを貼る**。RLSポリシーで使うカラムにインデックスがないとフルスキャンが走り、パフォーマンスが劣化する

**高速なRLSポリシーの書き方:**

```sql
-- 遅い書き方（避ける）
auth.uid() in (select user_id from team_user where team_user.team_id = table.team_id)

-- 速い書き方（推奨）
team_id in (select team_id from team_user where user_id = auth.uid())
```

**出典**: [Supabase Docs: Row Level Security](https://supabase.com/docs/guides/database/postgres/row-level-security) / [Supabase: RLS Performance Best Practices](https://supabase.com/docs/guides/troubleshooting/rls-performance-and-best-practices-Z5Jjwv)

#### APIキー管理

| キー | 用途 | 公開可否 |
|------|------|---------|
| `anon key` | フロントエンド用。RLSが有効な前提で設計された公開キー | 公開OK（RLS必須） |
| `service_role key` | RLSをバイパスする管理者キー | **絶対に公開禁止** |

**重要な注意点（2025年以降）:**
- 2025年11月以降、新規プロジェクトでは旧来のJWT形式の `anon`/`service_role` キーが廃止予定。新しいキー体系への移行を確認すること
- `service_role key` が漏洩すると、RLSを完全に無視して全データへのアクセスが可能になる
- キーは定期的にローテーションし、Supabaseダッシュボードの **Security Advisor** で定期チェックする

**出典**: [Zenn: Supabase利用時の最低限セキュリティ対策](https://zenn.dev/soooms/articles/144d2a4c85179d) / [Supabase Docs: API Keys](https://supabase.com/docs/guides/api/api-keys)

#### 認証設計のベストプラクティス

- Supabase Auth（メール/OAuth/MagicLink）を活用し、自前でパスワードハッシュ化等は実装しない
- JWTの有効期限を適切に設定する（デフォルト1時間は妥当）
- OAuthのリダイレクトURLは信頼できるドメインのみホワイトリスト登録

### 2-2. Vercel セキュリティ

#### 環境変数管理

| ルール | 理由 |
|--------|------|
| `NEXT_PUBLIC_` プレフィックスをシークレットに使わない | クライアントバンドルに含まれ、誰でも参照可能になる |
| 環境ごとに変数を分ける（Production / Preview / Development） | Preview環境に本番の認証情報が入ると、Preview URLへのアクセスで本番データが操作可能になる |
| 機密変数は「Sensitive」マークをつける | Vercelがマスキングして保存し、ログにも表示されなくなる |
| `.env` ファイルはGitにコミットしない | `.gitignore` に必ず追加 |

#### APIルートの保護

```ts
// APIルート・Server Actionでの認証チェック例
import { createClient } from '@/lib/supabase/server'

export async function POST(req: Request) {
  const supabase = createClient()
  const { data: { user } } = await supabase.auth.getUser()

  if (!user) {
    return new Response('Unauthorized', { status: 401 })
  }
  // 処理
}
```

- Server Actionsは**UIの制御に依存しない**。直接fetchで叩けるため、内部で必ず認証チェック
- Zodなどでリクエストのバリデーションを行う

#### レート制限

- Vercel自体にはアプリケーションレベルのレート制限機能がない
- **Upstash Ratelimit**（Redis）と Edge Middleware の組み合わせが定番
- レート制限なしの場合、AIのAPIコールを含むエンドポイントは高額請求リスクがある

#### セキュリティヘッダー

Vercelはインフラレベル（HTTPS・DDoS）は保護するが、アプリケーションセキュリティヘッダーは**自分で設定が必要**。

```js
// next.config.js
module.exports = {
  async headers() {
    return [
      {
        source: '/(.*)',
        headers: [
          { key: 'X-Content-Type-Options', value: 'nosniff' },
          { key: 'X-Frame-Options', value: 'DENY' },
          { key: 'X-XSS-Protection', value: '1; mode=block' },
          { key: 'Referrer-Policy', value: 'strict-origin-when-cross-origin' },
          { key: 'Permissions-Policy', value: 'camera=(), microphone=(), geolocation=()' },
        ],
      },
    ]
  },
}
```

#### Preview環境の保護

- Preview環境にはVercel認証またはパスワード保護を有効にする
- 本番と同じシークレットをPreview環境に設定しない

**出典**: [Vercel Docs: Sensitive Environment Variables](https://vercel.com/docs/environment-variables/sensitive-environment-variables) / [Vercel Academy: Security Review](https://vercel.com/academy/nextjs-foundations/security-review-apis-and-config) / [7 Vercel Security Mistakes](https://vibeappscanner.com/best-practices/vercel)

### 2-3. Git / GitHub セキュリティ

#### シークレットスキャン

シークレットが一度でもgit履歴に入ると、後から削除しても安全とは言えない（Gitの歴史は残る）。**予防**が最重要。

**推奨ツール:**

| ツール | 特徴 | 用途 |
|--------|------|------|
| **Gitleaks** | 軽量・高速。正規表現ベース。CI/CD統合が容易 | pre-commitフック + CI |
| **TruffleHog** | エントロピー検知で未知のシークレットも検出。S3・Docker等にも対応 | 定期的な全履歴スキャン |
| **GitHub Secret Scanning** | GitHubネイティブ。Push Protection機能でコミット前にブロック | パブリックリポジトリは無料 |

**pre-commitフック設定（Gitleaks例）:**

```bash
# gitleaksのインストール
brew install gitleaks

# pre-commitフックに追加
echo 'gitleaks protect --staged' >> .git/hooks/pre-commit
chmod +x .git/hooks/pre-commit
```

#### Git履歴の危険性

- `git log --all -p | grep -i "api_key\|secret\|password"` で過去の流出を確認できる
- 万が一シークレットをコミットしてしまったら: **まず即座にキーをローテーション/無効化**してから履歴の修正を行う
- 履歴から削除するには `git filter-repo`（`git filter-branch` は非推奨）を使うが、公開後では手遅れの場合がある

#### ブランチ保護

- `main` / `production` ブランチにはブランチ保護ルールを設定する
- 推奨設定: PR必須、レビュー承認1名以上、ステータスチェック必須、force pushを禁止

**出典**: [GitHub Docs: Secret Scanning](https://docs.github.com/code-security/secret-scanning/about-secret-scanning) / [Classmethod: Gitleaksコマンド解説](https://dev.classmethod.jp/articles/gitleaks-commands/) / [TruffleHog GitHub](https://github.com/trufflesecurity/trufflehog)

## 4. 優先学習ロードマップ

### フェーズ1（1〜2日）: 今すぐやるべきこと — 致命傷を防ぐ

**目標**: 今日の時点で存在する「即死レベル」の穴を塞ぐ

- [ ] **Supabase: 全テーブルのRLSが有効か確認**（Security Advisorで確認）
- [ ] **Supabase: `service_role key` がフロントエンドやGitに混入していないか検索**
- [ ] **Git: 過去のコミットにシークレットが含まれていないか Gitleaks でスキャン**
  - `gitleaks detect --source . -v`
- [ ] **Vercel: `NEXT_PUBLIC_` プレフィックスの環境変数にシークレットがないか確認**
- [ ] **Vercel: Preview環境の変数が本番と分離されているか確認**
- [ ] **GitHub: パブリックリポジトリにSecret Scanningが有効か確認**
- [ ] **`next.config.js` に最低限のセキュリティヘッダーを追加**（X-Content-Type-Options, X-Frame-Options）

### フェーズ2（1週間）: 基礎固め — 正しく設計できるようになる

**目標**: OWASP Top 10を理解し、自分のコードに当てはめて考えられるようになる

**Day 1-2: OWASP Top 10を読む**
- [OWASP Top 10 日本語版](https://owasp.org/Top10/ja/A00_2021_Introduction/) を通読
- 自分のアプリで該当しそうな箇所をメモ

**Day 3-4: Supabase RLSを完全に理解する**
- [Supabase RLS公式ドキュメント](https://supabase.com/docs/guides/database/postgres/row-level-security) を読む
- 既存プロジェクトのポリシーを見直し、ロールの明示・インデックスの有無を確認

**Day 5: APIルートと認証の見直し**
- 全APIルート・Server Actionで認証チェックが入っているか確認
- Zodでのバリデーションが実装されているか確認

**Day 6-7: PortSwigger Web Security Academy 入門**
- [XSSコース](https://portswigger.net/web-security/cross-site-scripting) の Apprenticeレベルを体験
- 攻撃者の視点で考える習慣をつける

**習慣化:**
- `npm audit` を定期実行（月1回）
- Gitleaksのpre-commitフックを全プロジェクトに設定

### フェーズ3（1ヶ月）: 実践レベル — スケール時に困らない設計ができる

**目標**: 新規プロジェクト立ち上げ時から、セキュリティを設計に組み込める状態

**Week 1: 攻撃を体験して深く理解する**
- PortSwigger Web Security Academy の主要4コースを完走
  - XSS / SQLインジェクション / CSRF / アクセス制御
- 「なぜその対策が有効か」を説明できるようになる

**Week 2: レート制限・監視を実装する**
- Upstash + Edge Middleware でレート制限を1プロジェクトに実装
- Vercel ログ・Supabaseログで異常アクセスをモニタリングする仕組みを構築

**Week 3: CI/CDにセキュリティを組み込む**
- GitHub ActionsにGitleaks + Snykを組み込む
- PRマージ前に自動でセキュリティチェックが走るパイプラインを構築

**Week 4: セキュリティチェックリストを自分用に作る**
- 新規プロジェクト立ち上げ時のセキュリティチェックリストをObsidianに作成
- OWASP ZAPで既存プロジェクトをスキャンし、残課題を把握

**スケール時に必要になる知識（余裕があれば）:**
- WAF（Web Application Firewall）の基礎
- 依存関係の自動更新（Dependabot）
- セキュリティポリシーの文書化（クライアント向け）

## まとめ

美しいコードと美しいサービスは、セキュリティの土台の上に立っている。専門家になる必要はないけれど、「RLSを有効にしていない」「service_role keyをクライアントに公開している」「シークレットがGitに混入している」——こういう致命的なミスだけは絶対に避けなければいけないよ。

フェーズ1のチェックリストは今日中に終わらせよう。1〜2時間あれば全部確認できる。その後、少しずつ学習を積み上げていけば、スケールしても恥ずかしくないアーキテクチャが自然と作れるようになるはずだよ。
